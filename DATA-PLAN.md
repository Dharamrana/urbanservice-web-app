### Java booking engine — `ServiceRequestService.java` + controllers
**Used by**: `quoteCart`, `createBooking`, `assignProvider`/rating/rescheduling/cancellation/payment and provider job actions
**Test command**: `sed -n '1,650p' src/main/java/com/urbancompany/clone/service/ServiceRequestService.java`; `cat controller/ServiceRequestController.java`, `controller/ProviderController.java`, `controller/ServiceProviderController.java`, `service/ServiceProviderService.java`
**Sample output** (exact rules extracted):
- `VISITING_FEE = 49.0`; `DAILY_SLOTS = ["08:00-10:00","10:00-12:00","12:00-14:00","14:00-16:00","16:00-18:00","18:00-20:00"]`.
- Cart: 1–20 lines, quantity 1–10 per line, price-locked from the DB at quote/booking time; `finalPrice = sum(unitPrice*qty) + 49.0`; address is required; scheduled date cannot be in the past, defaults to tomorrow with slot `"10:00-12:00"`; invalid slots rejected.
- Assignment: picking a provider sets `ASSIGNED` + generates a 4-digit `%04d` start OTP; no provider picked stays `PENDING`.
- Status transitions: `PENDING→{ASSIGNED,CANCELLED,REJECTED}`, `ASSIGNED→{IN_PROGRESS,CANCELLED,REJECTED,ASSIGNED}`, `IN_PROGRESS→{COMPLETED,CANCELLED}`, `COMPLETED→{}`, `CANCELLED→{}`, `REJECTED→{ASSIGNED}`.
- Reschedule only `PENDING|ASSIGNED` with a valid slot and non-past date; rate only `COMPLETED`, rating 1–5, rolling into the provider's average `((current*total)+rating)/(total+1)`; cancel blocked when `COMPLETED|CANCELLED`, and a `PAID` booking auto-refunds to `REFUNDED` on cancel.
- Mock payment: `initPayment` returns mode CASH passthrough, "Already paid" if `PAID`, otherwise creates `MOCK-<millis>-<requestId>`; `confirmPayment` matches the ref and moves `PAYMENT` to `PAID|FAILED`.
- Provider engine: pool = `PENDING` requests whose primary or any cart-item service is in the provider's `serviceIds`; accept requires available and moves to `ASSIGNED` + OTP; start requires `startOtp.trim()` equality then `IN_PROGRESS` + `otpVerified`; earnings = month-to-date completed `finalPrice` sum + active (PENDING/ASSIGNED/IN_PROGRESS) and completed counts + provider rating.
- Distance: Haversine `R=6371`, providers sorted nearest-first and filtered by availability for nearest queries.
**Processing**: these rules are re-implemented 1:1 in `server/src/actions.ts` (zod-validated). Booking creation validates cart lines against the seeded catalogue, recomputes prices server-side (never trusts client totals), generates a random 4-digit OTP, and enforces the same transition map, returning Result-style errors instead of throwing.

## Long-term data behavior
- **Refresh policy**: no refresh triggers (per build request). The catalogue is seeded once from `DataInitializer.java` (or on explicit Reset from Settings); bookings, ratings, availability, and OTP state persist in `app.db` via server actions and are read fresh on each open.
- **Growth**: bounded by user activity — services (8) and providers (8) are fixed reference rows; `bookings` and booking `items` grow by one row per user booking (each 1–20 lines). No external poller or scheduler adds rows.
- **Ordering**: services by the `DataInitializer` list order (Carpenter → Painter); providers sorted by Haversine distance from the current location (Delhi 28.6139,77.2090 default) — nearest first, with unavailable providers excluded from assignment but still listed as unavailable; bookings newest first by `created_at`; provider jobs grouped active-first then by scheduled date; pool by scheduled date ascending.
- **Time semantics**: `scheduled_date` is stored as a plain `YYYY-MM-DD` calendar date and `slot` as one of the six `DAILY_SLOTS` strings (no timezone conversion needed); `requested_at`/`completed_at` are stored as UTC timestamps and rendered in the viewer's `Asia/Kolkata` timezone. Date validity (not in the past) is checked in the server action in IST.

## Rejected approaches
- **Run the Java app as-is (Spring Boot + MySQL + Redis)** — rejected: the Muse artifact runtime has no Java 17/JVM, MySQL, or Redis; the artifact must be TypeScript. The booking logic is ported faithfully instead, preserving its user-visible behavior and constants.
- **Fetch service/provider data from an external API or invent placeholders** — rejected: the repo's `DataInitializer.java` is the authoritative catalogue; fabricating additional services, prices, or providers would misrepresent the user's project.
- **Real authentication with BCrypt/Spring Security sessions** — rejected by artifact constraints (no server-side session auth in the TypeScript runtime). The port keeps a lightweight profile setting (name/phone/address) for the booking wizard, faithful to the original signup prefill flow without pretending to be secure auth.
- **Hand-drawn map pins or fake distance badges** — rejected per artifact rules: distance is computed with the repo's exact Haversine and shown as a numeric `km away` label; if an interactive map is added it uses the artifact map reference, otherwise no map is shipped.

## Rapido-style select-on-map (edit)
- The customer booking location step and the provider service-area editor now use a Rapido-style picker on the same HatchMaps vector control: a fixed orange centre pin, live centre readout (nearest Dehradun locality via Haversine against the 8 AREA_PRESETS + exact coordinates), area search, locality chips, GPS, and a Confirm location button. HatchMaps exposes no centre getter, so the live centre is derived from the rendered locality markers' projected positions with Web Mercator math (`computeMapCenter` in client/src/maps.ts); no other renderer or tile source is used. If the map cannot render, search/chips/GPS/coordinates still set the location. No new data sources or seeded rows; labels never invent a street address — a pin away from every preset is labelled "Dropped pin near <locality>".
